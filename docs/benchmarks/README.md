# v0.1 基线实测记录（2026-09-13）

这些数据来自加入公式和 Mermaid 之前的版本，不代表 v0.2 图表密集文档的性能。

## 环境和方法

Linux x86_64；Rust 1.94；系统 Google Chrome；Python 3.12；Comrak 0.53；Playwright 1.62；pikepdf 10.13。Noto Sans/CJK/Mono CJK 字体已安装。基准语料包含中英日韩段落、标题、任务列表、表格与 Python 代码。文件按 MiB 生成，每个章节有唯一的首尾标记。

每个尺寸都必须通过完整 PDF 渲染与合并，再由 `pdftotext` 验证每个章节首尾标记、中文和所有标题目标。只成功规划 HTML 不计通过。内存包含完整 Worker 后代进程树，每 100ms 采样一次 RSS 总和；共享页可能重复计算。

## 已完成

- `cargo test`：常规 AST 分块、GFM、全局引用、唯一标题 ID。
- `cargo test --release oversized_acceptance -- --ignored`：5MB+ 代码块、100000 行表格、2000000 字符段落。所有片段低于预算；内容计数不丢失，表头重复。
- 13 项 PDF/预处理/故障注入集成测试：跨块链接、跨块脚注、书签、缓存复用、损坏 PDF 修复、SIGKILL 后拆分、单块继续拆分、超时与独立会话后代清理、本地资源变更检测、输入防覆盖、真实 Chromium 进程崩溃后重试、损坏但带有 PDF 文件头/尾的结果不会进入缓存、部分任务失败后的恢复、重复内容缓存隔离、代码前后空行保留。
- `cargo clippy -- -D warnings`：通过。
- 混合内容样例 PDF：已渲染 PNG 检查，正文和代码字体已嵌入，CJK 可提取。10/20/50MiB PDF 的首、中、末页面已抽查，无文字裁切或重叠；末页留白属于正常分页。

总耗时分别为 298.35、662.35、1601.20 秒，包含全文文字验证。PDF 大小分别为 45,375,281、90,805,215、227,531,234 bytes。

## 最终实现与基准证据的对应

最终协调器增加了严格 PDF 缓存校验、每个逻辑 Chunk 的独立标识及恢复修复。`scripts/verify_benchmark.py` 按文档顺序逐 Chunk 比较最终规划器生成的 HTML、静态预处理后的实际 Renderer HTML 和基准输入。该检查不依赖缓存文件名相同，也不取代真实 PDF 转换；它证明后续协调器修复未改变此次基准的浏览器负载。

保存的证据文件：`benchmark-results.json`、`benchmark-equivalence.json`、`pdf-audit.json`。大 PDF 和中间文件留在 `tmp/benchmark/`，不纳入源码交付。
